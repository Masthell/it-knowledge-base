## Теория и базовые концепции

**OWASP (Open Web Application Security Project)** — это некоммерческий фонд и глобальное сообщество, которое является «золотым стандартом» в области безопасности веб-приложений. Методология OWASP помогает разработчикам писать защищенный код, а пентестерам — проводить системный аудит.

> **💡 Ключевое правило:** 
> Безопасность — это процесс, а не результат. Использование OWASP позволяет внедрить проверку защищенности на каждом этапе жизненного цикла разработки (SDLC), а не только перед релизом.

- **Ключевой тезис:** > Методология OWASP предоставляет комплексный подход к обеспечению безопасности веб-приложений, охватывающий как выявление наиболее критичных рисков (Top 10), так и детальную верификацию защищённости на всех этапах жизненного цикла (ASVS), а также практические рецепты реализации защитных механизмов (Cheat Sheets).

В любой атаке на веб-приложение тесно связаны различные аспекты безопасности: инфраструктурный и прикладной. Например, уязвимость категории `Broken Access Control` (A01) может позволить злоумышленнику через атаку `SSRF` получить доступ к внутренней сети компании, взаимодействуя с сервисами, которые не должны быть доступны извне. Понимание того, где именно (на уровне сетевой инфраструктуры или на уровне кода приложения) находится проблема, помогает выбрать правильный инструмент защиты: устанавливать WAF (Web Application Firewall) для фильтрации вредоносных HTTP-запросов или настраивать межсетевой экран для ограничения доступа к внутренним портам.

OWASP как сообщество предоставляет три ключевых артефакта, каждый из которых решает свою задачу:
1. **OWASP Top 10** — это «заголовки новостей», список самых громких и распространённых угроз. Он служит для повышения осведомлённости разработчиков и менеджмента, а также для первичной оценки рисков.
2. **OWASP ASVS** — это детальный стандарт, который можно использовать как чек-лист для аудита безопасности приложения или как требования к подрядчику при приёмке работ. ASVS структурирован по разделам (V1–V14), каждый из которых содержит конкретные проверяемые требования с тремя уровнями глубины (Level 1, 2, 3).
3. **OWASP Cheat Sheets** — это практические руководства, отвечающие на вопрос «как именно это сделать безопасно?». Они содержат примеры кода, конфигураций и настроек для конкретных технологий и языков программирования.

**Эволюция OWASP Top 10:**
- Список обновляется раз в несколько лет на основе анализа реальных данных об инцидентах и уязвимостях.
- Актуальная версия на момент написания — **OWASP Top 10:2025**.
- Важное изменение в версии 2025 года: категория `SSRF` (Server-Side Request Forgery) теперь включена в **A01 Broken Access Control**. Это отражает понимание того, что SSRF — это по сути нарушение контроля доступа, позволяющее обойти сетевые ограничения и получить доступ к внутренним ресурсам, на которые у атакующего не должно быть прав.

**Место ASVS в методологии OWASP:**
ASVS предназначен для верификации технических аспектов безопасности приложения. Он не заменяет другие стандарты (например, PCI DSS или ISO 27001), а дополняет их конкретными техническими требованиями к коду и конфигурации. ASVS широко используется:
- Разработчиками как чек-лист при проектировании и написании кода.
- Пентестерами и аудиторами как основа для оценки защищённости.
- Заказчиками и менеджерами по закупкам как требования к безопасности приобретаемого ПО.

#### Глубокое погружение: OWASP Top 10:2025
В новой версии произошли важные изменения. Например, **SSRF (Server-Side Request Forgery)** теперь официально включен в категорию **A01: Broken Access Control**, так как это, по сути, нарушение контроля доступа к внутренним ресурсам сервера.

Является «золотым стандартом» того, как нужно делать правильно. |
| **Broken Access Control (A01)**                             | Нарушение контроля доступа — ситуация, когда пользователь получает доступ к данным или функциям, которые ему не разрешены.               | Классический пример: подмена идентификатора объекта в URL (`id=123` на `id=124`) и просмотр чужой информации.                                                                                                          |
| **SSRF (Server-Side Request Forgery)**                      | Атака, при которой сервер выполняет запросы от имени злоумышленника во внутреннюю сеть.                                                  | В OWASP Top 10:2025 SSRF включён в категорию A01, так как по сути является нарушением контроля доступа к внутренним ресурсам.                                                                                          |
| **Security Misconfiguration (A02)**                         | Ошибки конфигурации безопасности — оставленные по умолчанию настройки, лишние сервисы, отладочная информация в продакшене.               | Пример: панель администратора доступна по стандартному пути `/admin` с дефолтными учётными данными `admin:admin`.                                                                                                      |
| **Software Supply Chain Failures (A03)**                    | Сбои в цепочке поставок программного обеспечения — использование скомпрометированных или уязвимых сторонних библиотек и компонентов.     | Пример: установка вредоносного npm-пакета, который ворует переменные окружения (токены, ключи API).                                                                                                                    |
| **Cryptographic Failures (A04)**                            | Криптографические провалы — неправильное использование или отсутствие шифрования для защиты чувствительных данных.                       | Пример: передача пароля в открытом виде по HTTP или хранение его в формате Base64 (кодирование, а не шифрование).                                                                                                      |
| **Injection (A05)**                                         | Инъекции — внедрение злоумышленником своего кода, который выполняется интерпретатором на стороне сервера.                                | Классический пример: SQL-инъекция `' OR '1'='1` в поле логина для обхода аутентификации.                                                                                                                               |
| **Insecure Design (A06)**                                   | Небезопасное проектирование — архитектурные просчёты, которые невозможно исправить только настройками конфигурации.                      | Пример: отсутствие ограничения на количество попыток ввода кода из СМС, что позволяет осуществить перебор.                                                                                                             |
| **Authentication Failures (A07)**                           | Сбои аутентификации — слабая проверка подлинности пользователя.                                                                          | Пример: слишком короткие или предсказуемые пароли, отсутствие двухфакторной аутентификации (2FA) для критичных действий.                                                                                               |
| **Software and Data Integrity Failures (A08)**              | Сбои целостности программного обеспечения и данных — доверие к непроверенным данным или обновлениям.                                     | Пример: автоматическое обновление приложения по незащищённому протоколу HTTP без проверки цифровой подписи.                                                                                                            |
| **Logging and Alerting Failures (A09)**                     | Сбои логирования и оповещения — отсутствие или недостаточность записи событий безопасности, что не позволяет вовремя обнаружить атаку.   | Пример: атака продолжается неделю, но в логах нет записей о подозрительной активности или никто не настроил алерты на ошибки 500.                                                                                      |
| **Mishandling of Exceptional Conditions (A10)**             | Некорректная обработка исключений — приложение падает, зависает или раскрывает излишнюю техническую информацию при возникновении ошибок. | Пример: при ошибке SQL-запроса на экран выводится полный текст запроса с названиями таблиц и столбцов.                                                                                                                 |

---

- **ASVS Level 1** может быть проверен полностью автоматически и является минимальным барьером, который должно проходить любое приложение.
- **ASVS Level 2** требует ручной проверки многих аспектов, включая логику контроля доступа и обработку ошибок.
- **ASVS Level 3** подразумевает глубокий анализ архитектуры и подтверждение использования передовых методов защиты, таких как формальная верификация или детальный анализ потоков данных.
- Категория **A01 Broken Access Control** в версии 2025 года включает **SSRF**, что подчёркивает важность контроля не только прямого доступа пользователей, но и запросов, инициируемых самим сервером к внутренним ресурсам.
- **A03 Software Supply Chain Failures** — одна из наиболее быстрорастущих угроз. Для её mitigation необходимо использовать Software Bill of Materials (SBOM) и регулярно сканировать зависимости на известные уязвимости (например, с помощью OWASP Dependency-Check, Snyk, GitHub Dependabot).

**Технические нюансы ASVS:**
- ASVS состоит из следующих разделов (версия 4.x, актуальная структура):
    - **V1: Архитектура, проектирование и моделирование угроз**
    - **V2: Аутентификация**
    - **V3: Управление сессиями**
    - **V4: Контроль доступа**
    - **V5: Валидация, санитизация и кодирование**
    - **V6: Криптография на практике**
    - **V7: Обработка ошибок и логирование**
    - **V8: Защита данных**
    - **V9: Коммуникации**
    - **V10: Вредоносный код**
    - **V11: Бизнес-логика**
    - **V12: Файлы и ресурсы**
    - **V13: API и Web Services**
    - **V14: Конфигурация**
- Каждое требование в разделе имеет уникальный идентификатор, например, `V2.1.2` (Аутентификация → Устойчивость к перебору паролей). Требования сгруппированы по уровням: Level 1 (L1), Level 2 (L2), Level 3 (L3).

**Инструменты защиты на разных этапах обработки трафика (без привязки к OSI):**

| Уровень защиты                                       | Инструмент                          | Что он делает против OWASP Top 10                                                                                                                                      |
| :--------------------------------------------------- | :---------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Периметр сети**                                    | **Межсетевой экран / ACL**          | Ограничивает доступ к портам сервера базы данных (например, 3306, 5432) только с IP-адреса сервера приложений, предотвращая прямой доступ из внешней сети.             |
| **Периметр сети**                                    | **Защита от DDoS**                  | Подавляет SYN-флуд и другие атаки на истощение ресурсов сетевого стека.                                                                                                |
| **Прикладной уровень**                               | **WAF (Web Application Firewall)**  | Проверяет входящие HTTP-запросы на наличие сигнатур известных атак (SQL-инъекции, XSS, command injection) и блокирует подозрительные запросы.                          |
| **Прикладной уровень / Контроль исходящего трафика** | **NGFW (Next-Generation Firewall)** | Идентифицирует приложение, генерирующее трафик, и может блокировать подозрительные исходящие соединения (например, к командным серверам ботнетов).                     |
| **Шифрование трафика**                               | **TLS Inspection / SSL Visibility** | Расшифровывает HTTPS-трафик для проверки его содержимого на наличие вредоносного кода и последующего шифрования. Предотвращает атаки, скрытые в зашифрованных каналах. |


**Полезные шпаргалки (прямые ссылки на OWASP):**
- **[Cross Site Scripting Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)**: Как правильно экранировать вывод, чтобы избежать XSS. Включает правила для разных контекстов (HTML, JavaScript, CSS, URL).
- **[SQL Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)**: Использование Prepared Statements (параметризованных запросов) с примерами на Java (JDBC), .NET, PHP (PDO), Python, Go.
- **[Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)**: Правила хранения паролей, длины сессий и реализации 2FA. Охватывает все аспекты аутентификации: от проектирования до реализации.
- **[Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)**: Как солить и хешировать пароли. Рекомендации по выбору алгоритмов: Argon2id (предпочтительный), Bcrypt, PBKDF2.
- **[Docker Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html)**: Безопасность контейнеров (актуально для A03 - цепочки поставок). Включает правила для Dockerfile, запуска контейнеров, оркестрации.
- **[Kubernetes Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Kubernetes_Security_Cheat_Sheet.html)**: Защита кластеров K8s. Охватывает RBAC, Network Policies, секреты, безопасность подов.
- **[REST Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html)**: Рекомендации по безопасной реализации REST API: аутентификация (JWT, OAuth2), авторизация, валидация ввода, CORS.
- **[Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)**: Что и как логировать, форматы логов, защита логов от подделки.

**Интеграция Cheat Sheets в процесс разработки:**
- Добавьте ссылки на релевантные Cheat Sheets в Definition of Done для задач разработки.
- Используйте их как основу для код-ревью: ревьюер сверяет реализацию с рекомендациями из соответствующей шпаргалки.
- Включите ключевые положения Cheat Sheets в стандарты кодирования организации.

**Пример требования ASVS:**
- **Идентификатор:** `V2.1.2`
- **Текст:** Убедиться, что приложение ограничивает количество попыток аутентификации с одного IP-адреса или для одного аккаунта в заданный промежуток времени, чтобы предотвратить атаки перебором (брутфорс).
- **Применимые уровни:** L1, L2, L3.

**Как использовать ASVS для тестирования продуктов:**
1. **Определите контекст:** Какие данные обрабатывает продукт? Каковы регуляторные требования? Насколько критичен продукт для бизнеса?
2. **Выберите целевой уровень ASVS (L1, L2, L3).**
3. **Загрузите актуальную версию ASVS с официального сайта OWASP.**
4. **Создайте чек-лист,** включив в него все требования выбранного уровня из всех релевантных разделов.
5. **Проведите верификацию,** используя комбинацию автоматических сканеров (SAST, DAST, SCA) и ручного тестирования в зависимости от уровня.
6. **Задокументируйте результаты** по каждому пункту чек-листа, указав статус и комментарии.
7. **Предоставьте отчёт** с итоговой оценкой соответствия стандарту.

## Практика и настройка в реальной жизни

**Стандарт ASVS** — это главный инструмент для оценки продукта. Он имеет 3 уровня:

- **Level 1 (Базовый):** Можно проверить автоматическими сканерами. Обязателен для любого сайта.
- **Level 2 (Стандарт):** Требует ручного анализа кода. Для B2B и финансовых систем.
- **Level 3 (Критический):** Глубокий аудит архитектуры. Для банков и госструктур.

**Сравнительная таблица инструментов анализа:**

| Метод | Соответствие OWASP | Когда применять |
| :--- | :--- | :--- |
| **SAST (Статика)** | Весь код на наличие Injection | При каждом коммите разработчика |
| **DAST (Динамика)** | Проверка Top 10 на живом сайте | На тестовом сервере перед релизом |
| **SCA (Зависимости)** | Категория A03 (Supply Chain) | Всегда, чтобы не затянуть уязвимую библиотеку |

## Основные инструменты и утилиты

Шпаргалка по проектам OWASP:

- **OWASP ZAP** — бесплатный сканер (DAST) для поиска уязвимостей "на лету".
- **Dependency-Check** — сканер сторонних библиотек на наличие известных CVE (категория A03).
- **OWASP ModSecurity Core Rule Set (CRS)** — набор правил для WAF, который блокирует атаки из Top 10 на подлете.
- **ASVS Checklist** — Excel или JSON файл для проведения ручного аудита приложения.

**Пример из Cheat Sheet (Защита от SQL-инъекций):**
*Вместо склеивания строк в коде всегда используйте параметризованные запросы:*
```sql
-- ПЛОХО: query = "SELECT * FROM users WHERE id = " + inputID;
-- ХОРОШО: query = "SELECT * FROM users WHERE id = ?"; 
```

## Траблшутинг (решение проблем)

**Типовые проблемы внедрения OWASP:**

1. **Проблема: Сканер выдает 1000 уязвимостей, разработчики в панике.**
   - **Причина:** Плохая настройка (False Positives) или отсутствие приоритизации.
   - **Решение:** Начать с закрытия только **Top 10**. Использовать ASVS Level 1 как базовый фильтр.

2. **Проблема: WAF с правилами OWASP CRS блокирует обычных пользователей.**
   - **Причина:** Слишком строгие правила (Paranoia Level 4).
   - **Решение:** Перевести WAF в режим мониторинга на неделю, выявить легитимные запросы и добавить их в исключения.

## Вопросы

**Вопрос 1: Что такое OWASP ASVS и чем его уровни отличаются друг от друга?**
> **Краткий ответ:** Это стандарт верификации безопасности. L1 — автоматизированная проверка, L2 — ручной анализ для чувствительных данных, L3 — максимальная защита для критических систем.

**Вопрос 2: Где в списке OWASP Top 10 находится SSRF в версии 2025 года?**
> **Краткий ответ:** В категории **A01 Broken Access Control**. Раньше она была отдельной, но теперь считается частью нарушения прав доступа.

**Вопрос 3: Как бороться с уязвимостями в сторонних библиотеках (A03)?**
> **Ответ:** Использовать SCA-инструменты (например, OWASP Dependency-Check), вести SBOM (список всех компонентов) и регулярно обновлять зависимости.
